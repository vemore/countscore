# I18n

> Scope: how localisation is wired. For the procedure, use the `i18n-add-string` skill.
> Related: [[MobileApp]] · [[StoreListing]] · [[Testing]]
> Updated: 2026-09-20

## Facts

- **10 languages, 406 keys each, all translated** — no key missing in any file and no
  value left as the literal English string, both verified by `.claude/hooks/arb_keys.py`.
  `ar` · `de` · `en` · `es` · `fr` · `hi` · `ja` · `pt` (Brazilian) · `ru` · `zh` (Simplified).
  Arabic brings RTL.
- **Two checks, one script.** `arb_keys.py` compares key *sets* against the template and
  message *values* against `app_en.arb`. `SAME_AS_ENGLISH_OK` in that file lists the
  matches that are deliberate — `appTitle`, `artistName`, `backendUrlHint` everywhere, `ok`
  in fr/de/pt/ja, the `gameTypeName*` proper nouns, and ten more (`newGameNameLabel` in de among them) — and extending it is
  the intended escape hatch. `.claude/hooks/check-arb-sync.sh` runs both as a
  *non-blocking* report after every ARB edit; `guard-bash.sh` runs them separately at
  commit time, so its refusal names which one failed. [[Hooks]]
- **Unused keys are reported on demand only.** `arb_keys.py --unused` lists template keys
  that no `.dart` file under `lib/` mentions (the generated `app_localizations*.dart` aside).
  It runs in no hook: run it after removing a screen or a widget, and remove what it lists
  from all ten files.
- **`app_fr.arb` is the template**, `en` is the runtime fallback. This split is easy to get
  wrong: French carries all the `@key` descriptions (hence its 37 KB against 13 KB for
  English), English is what an unsupported locale resolves to.
- `l10n.yaml` is three lines: `arb-dir: lib/l10n`, `template-arb-file: app_fr.arb`,
  `output-localization-file: app_localizations.dart`. There is no `output-dir` and no
  `synthetic-package`, so generated files land in `lib/l10n/` and **are committed** —
  unlike `*.g.dart`, which is not.
- `pubspec.yaml` sets `flutter: generate: true`. Regenerate with `flutter gen-l10n`.
- The locale list exists **twice**: in the ARB files and again hardcoded in `main.dart`
  `supportedLocales`. Adding a language means touching both, or the ARB is generated and
  silently never selected.
- **Store locales are not app locales.** The Play listing under `store_listing/` uses Play's
  own codes (`fr` app ↔ `fr-FR` Play, `pt` ↔ `pt-BR`, `zh` ↔ `zh-CN`, `hi` ↔ `hi-IN`), and
  adding a language to `lib/l10n/` does **not** create the listing that makes it findable in
  that market — that is a separate directory, written by hand: [[StoreListing]].

### Usage

```dart
import '../l10n/app_localizations.dart';
final l10n = AppLocalizations.of(context)!;
Text(l10n.myString)            // plain
Text(l10n.welcomeUser('Alice')) // placeholder
Text(l10n.itemCount(5))         // ICU plural
```

### Long-form text is an asset, not an ARB key

The shipped game rules live in `assets/rules/rules_<locale>.md`, one file per app locale,
21 rulesets each — every built-in type but `Autre` — separated by `<!--@slug-->` marker lines. `lib/services/game_rules_catalog.dart`
parses and memoises them; `pubspec.yaml` declares the directory.

The ARB files stay for interface text. Four thousand words times ten languages would be
unreviewable as escaped JSON one-liners, and it would double again in the generated
`app_localizations_*.dart`, which this project commits. ICU escaping is the second reason:
`flutter gen-l10n` treats the apostrophe as an escape character as soon as a message has a
placeholder, and French prose is full of apostrophes.

What the ARB files give for free — ten locales that cannot drift apart — is kept by
`test/game_rules_catalog_test.dart`: every locale must define exactly the 21 slugs, none
empty, and must still carry the numbers the app scores on (100, 162, 56/51/41/36, Uno's
500, Président's 10, the ZapZap joker's 25, Farkle's 10 000, Canasta's 5 000 …), with
thousands separators — `1 000`, `1,000`, `1.000` — dropped before the lookup. A translation that loses a threshold
silently contradicts the game type it documents.

The text describes the scoring the type is **seeded** with (`lib/models/game_type.dart`),
and says how to flip it where tables commonly differ. French is the master and the nine
other files are translations of it. ZapZap is the one ruleset with no public source: its
text follows the author's own `GAME_RULES.md` in the ZapZap project, outside this
repository, and the analysis prompt's description of the game
(`KNOWN_GAME_TYPES["zapzap"]`, `backend/app/services/analysis/game_rules.py`) says the same
thing in English.

### Rules

- Never hardcode a user-facing string. `Text('Bonjour')` is a defect.
- Never hand-roll a plural. `'$n item${n > 1 ? "s" : ""}'` is a defect — use ICU plural
  forms in the ARB, because the categories differ per language (Russian has 4, Arabic 6).
- Dates and times keep going through `intl`'s `DateFormat`, which is already locale-aware.
- User-generated content — player names, scores, the names of game types the user created
  — is never translated. The **22 built-in** game types are the exception and are not
  user-generated: their displayed name comes from `gameTypeName*` through
  `lib/utils/game_type_name.dart`, keyed by `game_types.builtin_key`, and the name stored in
  the row is only a fallback. Renaming one clears the key, and from then on the rule above
  applies to it again.
- Every list of game types is ordered by the name it **shows**:
  `sortGameTypesByDisplayName` (`lib/utils/game_type_name.dart`), called by the game-types
  screen, the create-game dropdown, the home filter and the board's edit dialog.
  `DriftGameTypeRepository.getAll` returns rows in no order. The comparison is
  `collateNames` in the same file — no collator ships with the SDK or `intl`: case and
  Latin accents folded, katakana onto hiragana, voiced and small kana onto their base, `ー`
  read as the vowel it lengthens. `collateNames` leaves Han characters in code-point order;
  a **built-in** name sorts by its `gameTypeName*SortKey` ARB value instead
  (`builtinGameTypeSortKey`), which equals the name in nine locales and is the pinyin in
  `zh` — tone numbers after each syllable, one space between syllables (`qi2 ta1`), so a
  Chinese list reads in pinyin order with the Han names among the Latin ones by their
  initial. A custom Han name has no reading and stays in code-point order, after every
  Latin name. `test/utils/game_type_name_test.dart` pins the `fr`, `ja` and `zh` orders.

## Decisions & History

- **Pinyin sort keys for the built-in names, no collator (2026-09-19).** Twelve of the 22
  built-in names are Han in `zh`, and code-point order made that list look arbitrary. A real
  collator (`intl4x` and the like) brings ICU data to both the APK and the PWA for about
  twenty names, so each `gameTypeName*` got a `…SortKey` sibling: an ARB key must exist in
  all ten files, hence the name itself everywhere but `zh`. The spaces keep the order
  syllable by syllable (`qi` before `qiao`) and the tone numbers separate `拉米` from
  `拉密`. Custom names stay in code-point order. The same day, eight keys no screen read
  (`atLeast2PlayersRequired`, `filterByGameType`, `gameSettings`, `overallStatistics`,
  `playerNumber`, `playersListSummary`, `predefined`, `selectPlayer`) left all ten files.

- **The twelve long-tail rulesets were written in French and English, the eight other
  locales translated and then reviewed (2026-09-19).** As with the first nine, the texts
  are written for this app from the common knowledge of each game, not copied from a
  rulebook, and describe the scoring the type is seeded with; where editions or tables
  differ (Mille Bornes, Farkle, Triomino bonuses) the text says so rather than picking one
  silently. "The game ends when a total **reaches** N" is the wording everywhere, matching
  `GameType.isGameOver` since the same day; a player-elimination threshold still reads
  "exceeds" (ZapZap, Rami), because `playerDeadConditionType.over` is still strict. 6 qui
  prend is seeded 65 so that a player is out on reaching 66, as its box rule says, and its
  text no longer asks the user to set 65 themselves (fix/elimination-and-crown).

- **The game-type sort moved from the repository to the screens (2026-09-18).** `getAll`
  ordered `BY name`, the stored French literal, so a Japanese list read in French order once
  the displayed name came from `builtin_key`. The repository has no `AppLocalizations` and
  should not get one, so each screen sorts through one shared helper and the misleading
  `ORDER BY` went. The collation is a hand-written approximation of the UCA levels rather
  than a dependency: every collator on pub.dev brings ICU data or native assets to both the
  APK and the PWA, for a list of about twenty names. Pinyin order for `zh` is what it gave
  up.
  > **Status: Outdated** (2026-09-19) — the built-in names now sort in pinyin order in `zh`
  > through per-name ARB sort keys; only custom Han names remain in code-point order.

- **A built-in game type's name is localized; a user's is not (2026-09-16).** The seeded
  names were French literals, so a Japanese user started with a type called `Autre`. They
  could not simply be translated, because `name` was also the identity of the row in five
  places (see [[SchemaV10]]). `builtin_key` took over the identity and the displayed name
  together, which also makes the stored name harmless to overwrite between two devices in
  two locales. The ARB values of proper names (Yahtzee, Qwirkle, Uno…) are legitimately
  identical across most locales — the `gameTypeName*` prefix is exempt from the ARB
  value-equality check for that reason.
- **French is the template because the app was written in French first.** English is the
  fallback because it is the widest second language, so an unsupported locale degrades to
  something most users can read. The two roles being different files is a genuine footgun
  and the reason this page exists.
- **10 languages, chosen for reach.** Western (en, es, pt, fr, de), Asian (zh, hi, ja),
  Middle Eastern (ar, RTL), Cyrillic (ru) — roughly 5 billion native and secondary speakers.
- **The ARB check compares values, not only keys** (2026-09-16). Fourteen keys of the
  game-over cluster held the literal English string in `ar`, `hi`, `ja`, `ru` and `zh` while
  every check said the ten files were in sync, because every check counted keys. A Japanese
  user read "First player over" in a form label. The fix that matters is not the fourteen
  translations, it is that *present* can no longer be mistaken for *translated*:
  `arb_keys.py --values` compares against `app_en.arb`, and an allow-list — not a
  similarity heuristic — carries the handful of legitimate matches, so the check has no
  false positives and needs no judgement call to read.
  (`wip/done/2026-09-16-game-over-strings-untranslated.md`)
- **Uno and Président seed the box scoring, new databases only (2026-09-18).** Both were
  seeded lowest-wins, the house-rule reading, while the rules text described the box rule.
  They now seed highest-wins — Uno to 500, Président on the 2/1 barème to 10 — and the
  text matches. No migration touches `isLowestScoreWins` on an existing row: flipping a
  type that already has games would silently reverse finished standings
  (`test/seeded_scoring_test.dart`). (`wip/done/2026-09-16-uno-and-president-scoring-contradict-the-rules.md`)
- **Generated localisations are committed, generated Drift code is not.** Localisations
  change rarely and reviewing their diff is useful; `database.g.dart` is 7754 lines of
  churn. The inconsistency is intentional.
